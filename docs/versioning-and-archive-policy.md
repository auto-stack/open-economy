## 建议纳入Git的内容

以下分类已落实为本版规则。小型模型结果、固定基线的完整自有文档／书目快照、历史审计与五张自制模型图保留；源码检查没有发现嵌入整篇原文的长文字常量。实际纳管内容以提交树及忽略规则为准。

| 内容 | 建议 | 理由及边界 |
|---|---|---|
| `book`、`docs`、`shared`的原创文本 | 纳入 | 保存书稿、纲领、论证地位、术语与历史版本；不把日期更早的记录重写成最新状态 |
| `research/reviews`与`research/surveys`的原创综述、协议和比较表 | 纳入 | 保存问题、推理、实际读页、筛选及研究决策；其中整页扫描等附件另按来源类别处理 |
| `research/examples`、`research/tools`的程序及必要运行说明 | 纳入 | 使模型和归档流程可审阅；运行依赖及平台限制应说明 |
| 小型模型结果、固定评估协议、审计回执、不可替代的筛选与观察数据 | 选择纳入 | 虽可由程序生成，也可能是某一历史阶段的证据；不能一概忽略JSON、CSV或所有派生文件 |
| 人工书目、版本、URL、读页、获取失败、SHA256及原件清单 | 纳入经检查的最小记录 | 支持追溯。若字段内嵌原文或完整对话，另派生可公开记录，保留原档不改写 |
| 自制且正文实际使用的图表 | 纳入需要的版本 | 优先同时保存生成依据；区分原作图表与论文页面截图 |

已有`wiki/index`可作为来源入口，但机器目录、注释及冻结快照也应按实际字段检查，不能仅因位于索引目录就自动认定适合公开。原始元数据继续保存在本地档案，必要时由独立的精简目录进入Git。

## 保留在独立资料档案的内容

| 内容 | 建议 | 在Git中保留的对应信息 |
|---|---|---|
| 第三方论文PDF、整篇HTML和整页扫描 | 原件完整保留本地；以独立档案保存，逐项明确再分发条件后再决定公开副本 | 书目、实际版本、来源、读页、路径、SHA256与档案包索引 |
| 整页OCR、长篇提取TXT、包含原文词框的JSON | 按其来源与内容处理，与原件一起归档 | 识别引擎、范围、修订规则和公式核对记录；含长篇原文的文件不因转成文本就自动公开 |
| 原始AI对话及AutoOS商业讨论的完整导出 | 独立保存，逐项决定公开范围 | 经整理的原创论述与不含完整会话载荷的来源记录 |
| 扫描核对PNG与临时放大图 | 与相应来源一同保存，通常不进入主Git历史 | 图像页码、生成条件、原件与图像校验值、复核结论 |
| 搜索回包、服务器验证页面和其他获取响应 | 保留来源档案 | 执行查询、响应分类、失败与采用决定，不把验证页当成论文 |
| `__pycache__`、`.pyc`及可重建运行缓存 | 不纳入 | 保留生成程序与依赖说明即可 |

Git版本管理与对外公开是两个决定。这里依据当前公开远端安排纳管，不意味着第三方资料不能做本地版本管理；也不以是否能装入Git替代原件再分发范围的判断。二进制存储方案只处理体积与传输，不解决内容许可、私人会话和来源可追溯问题。

## 分开书稿包与来源包

**书稿包**包含可以公开的书稿、原创研究、模型、目录和校验信息；**来源包**保留下载原件、OCR、扫描及获取证据。两者用稳定编号、相对路径、版本和SHA256关联，`wiki/raw`继续作为本地来源目录，不需要为纳管而删除原件或改写旧manifest。

本轮独立ZIP已经生成，1358个档案按路径与SHA256列于[来源包清单](../wiki/archive/source-package-manifest.json)。它保存在被忽略的`.local-artifacts`，不随Git提交；原始文件仍在原位置。[检查工具](repository-validation.md)对精简书稿及安装原件的环境分别报告状态。

若来源包另存或不随Git分发，读者仅取得书稿包时，应能通过书目和来源链接理解引用；本地PDF链接要说明依赖可选来源包。检查工具应区分“仓库必需文件缺失”“可选来源包未安装”和“已安装档案校验失败”。不能在精简克隆上将几百个缺省原件一律报告为损坏，或反过来把缺原件宣称为校验通过。

冻结评估快照若很小且适合公开，可以随书稿包保存。含完整来源文字或大量图像的快照进入来源包，Git保留其清单和hash。二者的历史阶段结果不能因重新生成而被覆盖。

## 实施顺序与框架标签

1. 按上述用途建立候选清单，确认原创文本、模型、来源描述和第三方载荷的边界；抽查实际字段，不按扩展名直接放行。
2. 准备忽略规则与来源包说明，保留当前工作目录；检查待提交列表，确认书稿、代码、必要证据和引用入口齐全。
3. 建立本地版本化基线，验证精简书稿包可阅读，带来源包的完整工作目录可核验。提交和推送分别记录状态。
4. [框架收束](framework-baseline-readiness.md)达标后，在已提交的明确修订上建立附说明的`framework-v0.1`，列六部分与候选单元、主要论证链、已知未解假说和档案包清单。是否发布到远端另按实际操作记录。

标签不使用“理论已证明”“正式出版”或“商业模式验证完成”的含义。以后基础研究和章节结构发生变化，新增版本说明，不移动已有标签掩盖变化。
